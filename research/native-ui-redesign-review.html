Product UI review · 2026-10-08

Native UI should follow Flutter’s flow and Anycast 2.0’s visual system

The device preview exposed a gap in visual finish. The native branch already has v2 color, type, spacing, and shell work, but its navigation still differs from the current Flutter app and several screens mix migrated and legacy treatments.

Decision: preserve Flutter navigation and actions; apply the sand-based Anycast 2.0 visual language to every native screen. Keep the iOS 18 floor.

Flow Visual system States and access Implementation and QA

Keep the three Flutter destinations and their actions

Flutter currently opens Podcast, Playlist, and Discover. Podcast contains Inbox and Subscriptions. Search and Settings open from the page header, and the mini player sits above the bottom navigation.

The native v2 shell currently exposes Inbox, Queue, and Library, with Search in the bottom bar. That moves Subscriptions into Library and hides Discover from the primary navigation. The different entry points make the native app feel like a separate product even where the screens are polished.

Keep: repository and playback state, authentication, network requests, sorting semantics, gestures, and route outcomes. Change page composition only where needed to match the Flutter destination structure.

Complete the existing v2 migration instead of adding a second style layer

Theme.swift, TypographyV2, Metrics.swift, and the asset catalog already contain the sand/gold token system. The inbox shell and some screens use those tokens; other screens still call legacy style accessors or force dark appearance.

  • Use the light/dark sand palette, gold accent, type scale, spacing, radii, and motion already defined in the native design system.
  • Standardize page headers, cards, category controls, buttons, sheets, empty states, and feedback across all screens.
  • Use the Anycast 2.0 UIKit implementation and local screenshots as component references; bind them to native repositories and view models rather than its showcase data.
  • Keep artwork-led player screens in the fixed warm-dark treatment defined by the tokens.
  • Guard iOS 26 glass materials and provide the documented UIKit material fallback on iOS 18.
Constraint Anycast 2.0 targets iOS 26 Liquid Glass; native supports iOS 18. Glass cannot become the only surface implementation.

Make visual states and controls agree with their behavior

Every migrated page should cover loading, empty, error, long text, and missing artwork. Any visible button, swipe affordance, or disclosure must keep its current action and accessibility label.

  • Check light and dark appearances, including sheets, keyboard, and system bars.
  • Check Dynamic Type, VoiceOver labels, safe-area insets, and long CJK/Latin titles.
  • Keep mini player taps distinct from Play/Skip controls; preserve seek, reorder, dismiss, and transcript-follow gestures.
  • Do not add new destinations or features from exploratory Figma frames.

Implement in user-path order and verify on the device

  1. Align the root shell and header actions with Flutter’s Podcast / Playlist / Discover flow; place Inbox and Subscriptions inside Podcast.
  2. Finish Inbox, Subscriptions, Discover, channel, episode detail, Playlist, and mini player surfaces.
  3. Finish full player, transcript, search, chat, settings, auth, paywall, and import/share sheets.
  4. Update focused visual smoke, layout, navigation, and snapshot coverage while preserving business-logic tests.

Acceptance: the same seed data and actions produce the same Flutter flow; all native screens use one coherent 2.0 visual language; no core UI depends on iOS 26; iPhone 15 Pro review confirms safe areas, text sizing, and the main interactions.

Reference set inspected: current Flutter main.dart, BottomNavBar, MyAppBar, AnycastTheme; native v2 migration spec and UIKit design system; local Anycast 2.0 UIKit views and screenshots. Frame-level Figma MCP access is not available in this task session.
